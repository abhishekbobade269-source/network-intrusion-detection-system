# Model card — anomaly-detection model

Following the spirit of Mitchell et al.'s model cards (2019), scoped to
what's relevant for a single-model, single-purpose anomaly detector.

## Model details

- **Type**: Isolation Forest (`sklearn.ensemble.IsolationForest`) behind a
  `StandardScaler`, packaged as one `sklearn.pipeline.Pipeline` and
  serialized with `joblib` (`nids.ml.train`).
- **Task**: unsupervised anomaly scoring of one network flow, output as a
  calibrated score in `[0, 1]` (`nids.ml.predict.AnomalyScorer.score`),
  thresholded (default 0.5, `NIDS_ML_ANOMALY_THRESHOLD`) into a `Finding`
  when a flow looks sufficiently unlike training-time benign traffic.
- **Inputs**: the 26 flow-level features in
  `nids.ml.features.FEATURE_COLUMNS` — volumetric counts, packet-length
  distribution, inter-arrival timing, and TCP flag counts. No IP addresses,
  ports, or payload bytes are features (only carried as evidence/metadata
  on the resulting alert) — the model generalizes across hosts by design.
- **Training procedure**: fit **only on benign-labeled rows** of the
  training split (`nids.ml.train.train`) — this is an anomaly detector, not
  a supervised attack classifier, so it never sees attack examples during
  fitting. A held-out mixed (benign + attack) split is used purely to
  report evaluation metrics, since the datasets this loads happen to carry
  labels.

## Training data

Two supported sources (`nids.ml.datasets`):

1. **Synthetic** (`--dataset synthetic`, the default and the one used to
   produce the model shipped/tested in this repo): four Gaussian-ish
   clusters (benign, scan-like, flood-like, exfil-like) generated by
   `make_synthetic_dataset`. This exists **only** so the training →
   scoring pipeline is runnable and testable with zero external downloads
   (`tests/unit/test_ml_pipeline.py`, CI). **Its accuracy numbers are not a
   claim about real-world detection accuracy** — the clusters are
   hand-shaped to be separable, which is the point (pipeline validation),
   not evidence of real-world performance.
2. **CICIDS2017** (`--dataset cicids2017 --cicids-csv ...`): Sharafaldin et
   al.'s 2017 Canadian Institute for Cybersecurity dataset — realistic
   benign + labeled-attack traffic, in CICFlowMeter's own flow-feature CSV
   format, which is why `CICIDS2017_COLUMN_MAP` in `nids.ml.datasets` maps
   almost 1:1 onto `FEATURE_COLUMNS`. **Not bundled** (multi-GB, its own
   license/attribution terms) — download it yourself from
   <https://www.unb.ca/cic/datasets/ids-2017.html> and point `--cicids-csv`
   at the daily files you want.

**If you're evaluating this project's real-world detection quality,
retrain on CICIDS2017 (or your own labeled traffic) first** — anything
shipped/tested against the synthetic set is a pipeline-correctness check,
not an accuracy claim.

## Evaluation

`nids.ml.train.train` reports ROC-AUC, average precision, and a
`classification_report` at the 0.5 threshold on the held-out mixed split,
written to `models/<name>.metrics.json` alongside the joblib artifact
every time you train. Re-run training whenever you change the feature
schema, the dataset, or the model hyperparameters, and diff the new
metrics file against the old one before trusting a new model in
production.

## Known limitations

- **Distribution shift.** An Isolation Forest trained on one network's
  benign traffic shape will misfire on another network with a
  meaningfully different baseline (e.g. very different typical flow
  duration or packet-size mix) — retrain on your own representative
  benign traffic before relying on it, don't just ship the synthetic-data
  model.
- **No adversarial robustness.** See `docs/threat_model.md`'s explicit
  non-goals — an attacker who can shape their traffic's statistical
  profile can evade this class of detector.
- **Flow-boundary sensitivity.** `FlowRecord`'s features depend on
  `NIDS_FLOW_IDLE_TIMEOUT_S` / `NIDS_FLOW_ACTIVE_TIMEOUT_S` — changing
  those changes what a "flow" is, which changes the feature distribution
  the model was trained on. Retrain if you change the timeouts materially.
- **No periodic retraining pipeline.** Retraining is a manual `nids train`
  invocation today; there's no drift-detection or scheduled-retrain job
  included (a reasonable follow-up, not implemented).
